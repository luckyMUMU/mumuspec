# 开放问题

> 层级: Level 3 附录

---

## 核心设计问题

### 1. 多语言 AST 解析抽象

不同编程语言的 AST 解析差异如何抽象？tree-sitter 是否足够覆盖所有目标语言？

**关联**: Phase 3 — 代码图谱构建引擎

**当前倾向**: 以 tree-sitter 为基础解析层，针对语言特性差异提供 adapter 插件机制。

### 2. 规范继承冲突检测

当多层规范的 SHALL NOT 出现矛盾时（子层收紧到无法实现），如何自动检测和告警？

**关联**: Phase 1 — 规范加载引擎

**当前倾向**: 加载时进行约束可满足性检查（constraint satisfiability check），矛盾时报告冲突详情并阻断。

### 3. 图谱性能

大型代码库（10万+ 文件）的图谱构建和查询性能如何保证？

**关联**: Phase 3 — 代码图谱构建引擎

**当前倾向**: SQLite 嵌入式存储 + 增量索引（仅重新解析变更文件）+ 查询缓存层。

### 4. 规范版本化

规范本身也需要版本管理，如何处理规范版本与代码版本的对应关系？

**关联**: Phase 2 — delta spec 合并引擎

**当前倾向**: 规范随代码一同版本控制（git），delta spec 通过语义标记（ADDED/MODIFIED/REMOVED）记录变更历史。

### 5. 渐进式披露的精度

如何确保 AI 在跨模块工作时能正确加载所有相关规范，而不遗漏？

**关联**: Phase 1 — 树状规范加载引擎

**当前倾向**: 通过 `index.yaml` 概要 + 代码图谱依赖关系辅助判断需要加载的兄弟模块规范。

### 6. 与现有 lint 工具的关系

MumuSpec 的 Enforcement 是自研规则引擎，还是封装现有 lint 工具（ESLint/Semgrep/SonarQube）？

**关联**: Phase 1 — lint 规则引擎

**当前倾向**: 自研规则引擎为核心 + ESLint/Semgrep 插件适配器复用生态规则。

### 7. 团队协作

多人同时修改规范时如何处理冲突？是否需要规范评审流程？

**关联**: Phase 2 — 变更生命周期

**当前倾向**: 单一活跃变更约束自然序列化规范修改；未来考虑引入规范评审（spec review）作为 Archive 子流程。

## 契约层问题（0.8.0 新增）

### 8. 契约与外部服务的同步策略

外部服务的 API 变更如何自动感知？是否需要集成外部服务的 OpenAPI/proto 自动拉取机制，还是依赖手动更新契约文件？

**关联**: Phase 3 — 契约图谱集成

**当前倾向**: 
- MVP 阶段依赖手动更新契约文件
- 未来探索：定时拉取外部服务 OpenAPI/gRPC reflection → diff 对比 → 生成变更提醒
- 需要考虑外部服务的认证机制和拉取频率

### 9. 契约约束与手写规范的冲突解决

当契约派生的 SHALL/SHALL NOT 与手写的 SHALL/SHALL NOT 出现矛盾时（如契约要求 5s 超时，手写规范要求 3s），如何检测和解决？

**关联**: Phase 3 — 契约约束派生引擎

**当前倾向**:
- 检测：派生约束注入时与已有约束进行语义对比（ID 前缀区分来源）
- 解决优先级：用户显式指令 > SHALL NOT > SHALL > 契约派生约束 > 默认
- 冲突时阻断并报告，由用户决策保留哪个约束

### 10. 契约的跨项目共享

多个微服务项目是否需要共享契约仓库？如何建立契约的跨项目引用与版本对齐机制？

**关联**: Phase 5 — 生态与分发

**当前倾向**:
- 方案 A：独立契约仓库（contract registry repo），各项目通过 git submodule 或 npm 包引用
- 方案 B：去中心化模式，各项目维护自身 outbound 契约，消费方通过拉取对方契约仓库建立 external 契约
- 需要进一步评估团队规模和微服务数量

### 11. 契约 Schema 的共享与复用

多个契约之间的公共数据结构（如分页响应、错误码格式）如何复用？`schemas/` 目录的引用机制如何设计？

**关联**: Phase 3 — 契约图谱集成

**当前倾向**: `$ref` 引用机制（类似 OpenAPI），支持本地引用和跨包引用。

### 12. 契约变更的通知机制

当 outbound 契约发生变更时，如何通知已知的外部消费方？

**关联**: Phase 4 — CI/CD 与自动化

**当前倾向**: Archive 阶段生成契约 changelog，通过 webhook / 通知渠道推送给注册的消费方。

## Top 3 技术风险验证 Sprint

以下三个风险项是 MumuSpec 实现阶段最关键的不确定性，需要在 Phase 3 启动前进行验证 Sprint。

### 风险 1: 多语言 AST 解析抽象

**风险描述**: tree-sitter 是否能覆盖所有目标语言（TypeScript/Java/Go/Python/Rust）的 AST 解析需求？

**备选方案对比**:

| 方案 | 优势 | 劣势 | 覆盖语言 |
|------|------|------|----------|
| **tree-sitter** | 多语言、增量解析、性能好 | 需要为每种语言安装语法包 | 40+ 语言 |
| **Babel + TypeScript** | 深度支持 JS/TS 生态 | 仅 JS/TS，无法扩展 | JS/TS |
| **各语言原生 AST** | 解析最精确 | 每种语言独立集成，维护成本高 | 取决于集成 |
| **ripgrep + 正则** | 极轻量、无依赖 | 无法理解语义，仅模式匹配 | 任意文本 |

**决策截止时间**: Phase 3 启动前（T+7 周前）

**验证 Sprint 安排**:
- Sprint 周期: 3 天
- 验证内容: tree-sitter 解析 TypeScript + Java + Go 各 1000 文件，检查 AST 节点覆盖率和解析耗时
- 通过标准: 解析成功率 ≥ 95%，单文件解析 < 50ms
- 降级方案: 不支持的语言降级为文件级索引（无函数/类级绑定）

### 风险 2: 10万文件图谱性能

**风险描述**: SQLite + 增量索引方案在 10万+ 文件的大型代码库中是否满足性能要求？

**备选方案对比**:

| 方案 | 存储类型 | 查询性能 | 增量更新 | 运维成本 |
|------|---------|---------|---------|----------|
| **SQLite + 增量索引** | 嵌入式 | < 500ms（典型查询） | 支持 | 零（嵌入式） |
| **Neo4j** | 图数据库 | < 100ms（图遍历） | 需全量重建 | 高（独立服务） |
| **内存图 + 持久化** | 内存 | < 50ms | 支持 | 低 |
| **DuckDB + SQL 图查询** | 嵌入式分析 | < 200ms | 支持 | 零 |

**决策截止时间**: Phase 3 启动前（T+7 周前）

**验证 Sprint 安排**:
- Sprint 周期: 5 天
- 验证内容: 构造 10万文件模拟项目，测试全量索引耗时、增量索引耗时、典型查询（影响分析/调用链追踪）延迟
- 通过标准: 全量索引 < 5min，增量索引 < 10s，查询 < 500ms
- 降级方案: 大型项目降级为文件级图谱（不索引函数/类级节点）

### 风险 3: 规范继承冲突检测

**风险描述**: 多层规范的 SHALL/SHALL NOT 冲突检测算法是否可行？约束可满足性检查（SAT）的复杂度如何？

**备选方案对比**:

| 方案 | 检测能力 | 性能 | 实现复杂度 |
|------|---------|------|-----------|
| **规则匹配**（字符串/正则） | 浅层冲突检测 | < 100ms | 低 |
| **语义对比**（AST + 同义词） | 深层冲突检测 | < 1s | 中 |
| **SAT 求解器** | 完整可满足性检查 | NP-hard，可能超时 | 高 |
| **AI 辅助检测** | 语义级冲突检测 | < 5s（API 调用） | 低（但依赖外部 API） |

**决策截止时间**: Phase 1 启动前（T+3 周前）

**验证 Sprint 安排**:
- Sprint 周期: 2 天
- 验证内容: 构造 20 组冲突/不冲突的 SHALL+SHALL NOT 对，测试规则匹配方案的准确率
- 通过标准: 规则匹配准确率 ≥ 80%（剩余通过 AI 辅助或人工审查补充）
- 降级方案: 冲突检测降级为 WARN 级别（不阻断加载，仅提示）
