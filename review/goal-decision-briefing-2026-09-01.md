## D1（=C2）Rules 生成与已有文件的冲突策略

### 已核实事实

1. 生成目标有三类占用状态：不存在 / mumuspec 托管（带 `> Auto-generated by MumuSpec` 标记头，本项目 AGENTS.md 已是该形态）/ 用户手写。
2. CLI-first 原则要求数字化流程（CI、agent 调用）可非交互完成——交互式询问与该原则冲突。
3. Git 是硬依赖（A-01），任何被覆盖内容都有版本兜底。

### 选项对比

| 选项 | 行为 | 优点 | 缺点 |
|------|------|------|------|
| **A. 标记分路（建议默认）** | 无标记头（用户手写）→ 跳过 + 警告 + `--force-rules` 接管提示；有标记头 → 幂等更新；不存在 → 直接生成 | 零数据丢失；托管文件可幂等滚动；非交互友好 | 用户文件可能缺规范链 → 由 `doctor` / `check` 补"规范保护降级"警告 |
| B. 覆盖前询问 | 交互式确认 | 引导性强 | 破坏 CI / agent 非交互流；需要 TTY；与 CLI-first 冲突 |
| C. 一律跳过 | 从不写已存在文件 | 最保守 | 托管文件无法滚动更新，规范链内容悄然过期 |
| D. 注入合并段 | 向用户文件追加托管段落 | 保留用户内容 | Markdown 合并脆弱、清理困难、边界模糊（违反 BOUNDARY 精神） |

### 建议默认值：A（按文件粒度执行，AGENTS.md 与 CLAUDE.md 各自独立判定）

## D2（=C3）停止生成 .cursorrules / .windsurfrules

### 已核实事实

1. **mumuspec 从未实现过 legacy 文件生成**——README 宣称自动生成，代码中生成器缺位（评审 G1 证据）。因此 C3 的实质是"新生成器**不要顺手兼容**遗留格式"，而非"撤回已有行为"，破坏面比字面小得多。
2. 生态现状：Cursor 原生读 `.cursor/rules/*.mdc` + AGENTS.md（.cursorrules 仅 legacy 兼容）；Windsurf 原生读任意目录 AGENTS.md；唯一必须薄壳的是 CLAUDE.md（Claude Code 不读 AGENTS.md）。
3. 本仓库根目录并无 .cursorrules——连自家 dogfood 都未依赖它。

### 选项对比

| 选项 | 行为 | 评估 |
|------|------|------|
| **A. 立即停止生成 + doctor 迁移提示（建议默认）** | 新生成器只产 AGENTS.md + CLAUDE.md/GEMINI.md 薄壳；doctor 检测到 legacy 文件时打印一次性迁移建议；release note 说明 | 单一事实源立即成立；**停止生成 ≠ 删除存量**（永不自动删用户文件） |
| B. 过渡期继续生成 | 到 0.21 再停 | 无意义——生成器本来就不存在，"继续"无从谈起 |
| C. 建迁移命令 `mumuspec migrate-rules` | 确认后删除/改名 legacy 文件 | 违反 Ponytail L1（YAGNI）：存量用户手工删一次即可，不值得一个命令 |

### 建议默认值：A，且不建迁移命令（C 否决），doctor 提示 + release note 承担迁移沟通

## D3 两个存量活跃变更的处置（决定 W0 推进节奏）

### 已核实事实（2026-09-01 实测）

1. `loop-auto-evaluate`：phase=**build**，2026-08-09 后**停滞 23 天**；test cases **未锁定**（与红绿 TDD 门禁矛盾，属历史遗留状态）；affected_scopes 为空；其对应实现 `src/core/metrics/auto-evaluate.ts` **已存在于源码**——完成度可能过半，不宜贸然 discard。
2. `meta-spec-evolution`：状态文件为**远古 schema**（`status:` 字段、无 `phase:`/`branch:`/`build_layers:`），created 与 completed 同日（2026-08-09），工件齐全（proposal/design/tasks/verify）；`mumuspec status` 对它**直接崩溃**（TypeError: build_layers undefined）——暴露 CLI 对旧 schema 无容错，这是一个独立小缺陷。
3. 两者影响域与 W0（install / guard / change 工件 / 文档）**几乎无交集**。

### 选项对比

| 选项 | 行为 | 评估 |
|------|------|------|
| A. 严格串行 | 先收尾/归档两个旧变更，再放行 W0 | 最符合"单一活跃变更"字面；成本约 0.5–1 天，且需先给 loop-auto-evaluate 补测试锁定，节奏被拖住 |
| **B. 挂起容忍（建议默认）** | 三者并存至 W0 归档（旧变更均无活跃动作，交集为空，per-scope 约束未实质违反）；W0 归档后**第一个 W1 工单**收尾旧变更；顺手修 status 对旧 schema 的容错 | W0 立即推进；旧变更获得确定性收尾窗口；容错修复独立小 PR |
| C. 立即 discard meta-spec-evolution | 快 | 工件齐全直接丢弃可惜（其中含 meta 演化设计知识），至少应归档提取知识而非 discard |

### 建议默认值：B + 附带义务（status 容错修复提为 hotfix 级小单；W1 开头收尾两旧变更）

## D4 Wave 2 排序偏好：完备性深化 vs 生态深化

### 事实与权衡

| 维度 | 方案 X：完备性优先（W2-1 SHALL 自动化 → W2-2 反向通道 → W2-4 next → W2-3 JIT） | 方案 Y：生态优先（W2-4 next → W2-3 JIT → W2-1 → W2-2） |
|------|------|------|
| 与核心目标的关系 | **直接同轴**："大模型判定完备"的说服力取决于机械地基能否延伸到 SHALL 侧与反向盲区 | 间接：改善上手与 token 成本，完备性主张停留在 v1 双签 |
| 用户可感知收益 | 短期较低（引擎层） | 短期较高（编排入口、上下文更省） |
| 依赖关系 | W2-1 依赖 verifier-classify 扩展；W2-2 依赖 drift 扩展 | W2-4 依赖 W0-B 状态字段——做 X 期间自然就绪 |
| 差异化护城河 | 强（可验证性一等语义贯彻到 SHALL） | 弱（编排入口各家都有同类物） |

### 建议默认值：X（完备性优先）。理由：目标修正后，"LLM 判完备"的可信度是整个理念成立与否的承重墙；W2-4 在 X 尾部作为低成本高感知收尾。
