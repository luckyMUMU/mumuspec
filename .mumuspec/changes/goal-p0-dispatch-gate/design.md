# Design: goal-p0-dispatch-gate

> 阶段：design（草案，待人工确认后锁定测试）｜基准：proposal + 3 份 delta-specs + KP-0060 + 裁决 D1–D4
> 设计顺序声明（KP-0060）：本设计按"**规则 schema 与校验器 → 引擎 → skill 指引**"组织，每个新增 LLM 产出物先有校验器。

## 1. 主线 A：分发层 canonical-first

### 1.1 模块与边界（自顶向下）

```
src/install/
├── installer-registry.ts    [改] AgentType + 'codex'|'windsurf'|'gemini'|'copilot'
│                                 AGENT_RULE_TARGETS（声明式规则目标表，新增）
├── installer-ops.ts         [改] 各 agent 落盘路径接线；skill 目录式分发统一
└── rules-generator.ts       [新] 纯函数渲染器：input(规则目标+规范上下文) → output(文件内容三态判定)
src/doctor.ts（或既有 doctor 模块）[改] legacy 存量检测 + 规范保护降级警告
```

- **`AGENT_RULE_TARGETS` 是规则的唯一持有处**（KP-0060"规则归 LLM/配置"）——每个 agent 声明：`{ rulesFile: 'AGENTS.md', bridges: { claude: 'CLAUDE.md', gemini?: 'GEMINI.md' }, skillsDir, marksManaged: true }`。新增 agent = 只改这张表，不改渲染逻辑。
- **`rules-generator.ts` 不做 IO**（纯函数，返回 `{ path, content, action: 'create'|'update'|'skip' }[]`），落盘由 installer-ops 执行——可测性与 BOUNDARY 清晰。

### 1.2 生成物契约

| 文件 | 内容 | 冲突策略（D1） |
|------|------|---------------|
| `AGENTS.md` | 规范链摘要 + Ponytail 约束 + CLI 速查 + MCP 入口指引；标记头 `> Auto-generated by MumuSpec. Do not edit manually.`；目标 ≤200 行（Codex 32KiB 预算内） | absent→create；managed→update；user→skip+warn（`--force-rules` 接管） |
| `CLAUDE.md` | 薄壳：首行 `@AGENTS.md`，第二行起一行说明 | 同上，独立判定 |
| `GEMINI.md` | 薄壳（可选，gemini agent 安装时生成） | 同上 |
| `.cursorrules` / `.windsurfrules` | **不生成**（D2） | doctor 检测存量→一次性迁移提示 |

### 1.3 installer 扩展（+4，additive）

| Agent | Rules | Skills | 备注 |
|-------|-------|--------|------|
| codex | AGENTS.md（合并 home/repo/cwd，32KiB 预算） | `~/.codex/skills/` 目录式 | |
| windsurf | AGENTS.md（任意目录 nearest-wins） | 同通用 | 成本最低 |
| gemini | GEMINI.md 薄壳 + settings.json `context.fileName` 指引文档 | 同通用 | |
| copilot | AGENTS.md（nearest-wins，零额外文件） | `.github/` 不动 | |

Skill 分发统一为目录式 `SKILL.md`；phase-open/design/build/verify/archive + workflow-presets 全 agent 可装（解除 workbuddy 独享）。

## 2. 主线 B：完备性门禁 v1

### 2.1 工件 schema（version: 1，先有 schema 后有消费者）

```yaml
# open-questions.yaml（assumptions.yaml 同构，键名 assumptions）
version: 1
change: <name>
items:
  - id: OQ-1                      # AS-1 for assumptions
    question: <string>            # assumption: <string>
    status: open                  # open | resolved | accepted | deferred
    resolution?:                  # status != open 时必填
      decision_ref: <decisions.md 条目 id>   # 交叉断言目标
      note?: <string>             # deferred 必填理由
```

### 2.2 校验器（fail-closed）

- 位置：`src/change/artifact-validator.ts`（新，纯函数 + 诊断）。
- 校验层级：schema 层（version 存在、字段类型、status 枚举）→ 语义层（status≠open ⇒ resolution 存在且 decision_ref 可在 decisions.md 命中；deferred ⇒ note 必填）。
- 错误码：新增 `E-CHANGE-020`（工件 schema 非法）/ `E-CHANGE-021`（resolution 链断裂）。guard 不消费非法工件——**拒绝执行而非降级**（KP-0060 公理 3）。

### 2.3 phase-guard 挂钩点（仅两个转换）

| 转换 | 机械判定（guard 唯一依据） | LLM 角色 |
|------|--------------------------|---------|
| design→build | `open-questions.yaml` 存在且所有 items status≠open（或无该文件且 design.md 声明"无未决问题"→ 仍需人工签收标记） | 工件内容由 skill 指引 LLM 起草；**advisory 结论不进 guard 判定路径** |
| build→verify | 同上对 `assumptions.yaml` | 同上 |

双签语义：**LLM 起草（产出工件）+ 人签收（resolution 链即签收记录，落 decisions.md）**。无签收记录 → block，与 LLM 自评结论无关（ENF-3/ENF-4 对应实现）。

### 2.4 与既有机制的关系

- 复用 grill-me consensus gate：设计阶段的追问-签收环即工件 items 的生产者与消解者。
- 机械四分类一票否决**不动**：本门禁只增不改既有 guard 语义。
