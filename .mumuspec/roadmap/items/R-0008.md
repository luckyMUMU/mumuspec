# R-0008: next 结构化编排命令

## 背景

> 为什么需要这个目标？当前痛点是什么？不做的后果？

`getNextPhaseHint`（src/change/decisions.ts:87-105）仅覆盖 5 种纯 phase 驱动情形，不感知 verify_result==fail 挂起、build_pause、工件缺失、BP 等待状态——skill 承诺的"结构化菜单"（已完成/待完成/可执行操作）没有 CLI 实现，编排知识只能活在 skill 文本里。这是 2026-08-29 盘点发现 6 处 skill↔CLI 不一致的结构性根因：LLM 每次会话重新推导编排，漂移不可检。

## 范围

### 包含（Includes）
- `mumuspec next <name>`：单一入口回答"当前该做什么"——phase/workflow、阻塞点等待状态、guard 最近失败原因与修复命令、工件缺失清单、tasks 剩余计数、按情形生成的可执行操作菜单
- 吸收 `state check <phase> --recover` 的"恢复上下文"承诺（5 个 phase skill 均已承诺、实现未兑现——实现只做 4 项完整性检查，state.ts:359-457）
- `--json` 结构化输出（schema 冻结 v1：`{ phase, workflow, pending: [...], blockers: [...], suggested_actions: [...] }`）
- 各 phase skill 的"上下文压缩恢复"节改指向 `next`

### 不包含（Excludes）
- 任何自动执行的转换（只建议不执行——转换属用户确认域）
- 决策内容本身（brainstorming/设计/批判仍为 LLM 决策域）
- 多变更并行编排（single_active_change 语义不变）

## 验收标准（DoD）

| # | 验收条件 | 验证方法 |
|---|---------|---------|
| 1 | 至少识别 4 类挂起态（verify_result=fail / build_pause=plan-ready / 工件缺失 / BP 等待）并给出对应建议命令 | 每类一个 fixture 的单元测试 |
| 2 | `--json` 输出 schema 稳定且文档化 | schema 文档 + JSON 断言测试 |
| 3 | 5 个 phase skill 恢复节引用 `next`，不再让 LLM 手推恢复步骤 | skill 文本走查（R-0009 校验器通过） |
| 4 | `getNextPhaseHint` 原 5 情形行为被 `next` 全覆盖（status 命令复用） | 回归测试 |

## 工作量预估

`capacity_cost`: 2（schema 设计 0.5 + 实现 1 + skill 接线与测试 0.5）

## 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 输出 schema 过度设计（试图穷举所有状态） | 中 | 高 | v1 冻结最小集：4 类挂起态 + 既有 5 情形；扩展走增量 |
| 与 dashboard/status 输出重复 | 中 | 低 | `next` 为判定层，status/dashboard 为渲染层，复用 getChangeStatusSummary |
