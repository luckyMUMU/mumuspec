# R-0001: Graph 编排引擎

## 背景

> 当前 MumuSpec 的五层能力栈在 L5（Graph Engineering）为空白。现有 `graph.ts` 仅为状态机静态校验器，无法执行多模块并行编排。
> 当变更涉及多个需要并行验证的子系统时（API + DB + 前端 + CI），顺序串行执行效率极低。

## 范围

### 包含（Includes）
- **新建 `src/core/graph-orchestrator/`** — DAG 生成算法（基于 BOUNDARY.md 节点 + Contract Registry 边）
- **并行执行调度器** — 无依赖模块同时分配独立 worktree + agent context
- **拓扑序串行调度** — 依赖感知的执行队列
- **Graph 状态面板** — CLI Dashboard 实时输出每模块执行状态
- **失败隔离** — 单点失败不影响无依赖模块继续执行
- **与 Loop Engine 集成** — Graph 的每个节点可内嵌 Loop 模式

### 不包含（Excludes）
- Graph 可视化前端（VS Code 扩展留作后续）
- 多模型混合编排（R-0007 的范围，每 Agent 独立选模型）
- 跨仓库分布式 Graph（仅单仓库多模块）

## 关键设计决策

**与现有 `graph.ts` 的关系**：不扩展现有 `graph verify` 命令，而是新建独立的 `graph-orchestrator/` 引擎，完成后将 `graph.ts` 迁移为引擎的验证前端。

**worktree 资源管理**：最大并行度 = min(独立模块数, 4)，超出上限回退到串行子批次。

**Agent Context 隔离**：每个模块执行时携带独立的 scope-based knowledge context，禁止跨模块共享状态。

## 验收标准（DoD）

| # | 验收条件 | 验证方法 |
|---|---------|---------|
| 1 | 输入 3 模块 + 依赖关系，DAG 生成正确拓扑序 | 单元测试验证 |
| 2 | 无依赖模块并行执行 | 2 个独立模块同时 worktree + 评估 |
| 3 | 有依赖模块按拓扑序串行执行 | 依赖模块完成后才启动下游模块 |
| 4 | Graph 执行状态实时可观测 | CLI Dashboard 输出每模块状态 |
| 5 | 单点失败不影响其他独立模块 | 模块 A 失败时，无依赖的模块 C 继续执行 |
| 6 | 至少 8 个单元测试覆盖核心调度逻辑 | vitest 测试通过 |

## 工作量预估

`capacity_cost`: 8（≈ 16-24 人天）— 较原 R-0006 上调，因 scope 明确为新引擎而非扩展现有命令。

| 子任务 | 预估（人天） |
|--------|-------------|
| DAG 生成算法（BOUNDARY → 拓扑序） | 4 |
| 并行执行调度器（worktree + context 隔离） | 5 |
| 状态面板（CLI Dashboard） | 2 |
| Loop Engine 集成层 | 3 |
| graph.ts 迁移重构 | 2 |
| 测试 + 文档 | 5 |

## 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| Worktree 资源耗尽（大规模 Graph） | 中 | 高 | 限制并行度 ≤ 4 + 串行 fallback |
| 循环依赖检测遗漏 | 低 | 高 | DAG 生成时严格拓扑排序校验 |
| Agent 上下文污染 | 中 | 中 | 严格隔离每个模块的 context scope |
| 与现有 Loop 流程兼容成本超预期 | 中 | 中 | Graph 作为 opt-in `--parallel-graph` flag 启动 |

## 互斥理由（Mutex Rationale）

> 为什么不能与 `R-0005`（Meta-Spec Evolution）同时进行？

R-0001 涉及 runtime 架构大改（新增 graph-orchestrator 引擎、worktree 管理、并行调度器），会大规模修改执行层代码。R-0005 涉及 Guard Layer 语义升级和元进化框架，会大规模修改规范层代码。两者同时进行会产生架构注意力分散，且任何一方的设计变更都可能影响另一方的集成点。建议 R-0001 完成 stable API 后再启动 R-0005。
